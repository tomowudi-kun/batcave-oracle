# Signed public confirmation transfer

Solves the observed clipboard/account/remote-desktop handoff failure. Cortana's existing protected signer still runs locally and asks the owner for the existing passphrase. After it creates the public proof, the generated PowerShell command submits only that JSON to the separate `batcave-first-proof-v1` endpoint. The original authenticated owner page retrieves the verified public proof automatically. Finish enrollment remains a separate action through the unchanged JWT-protected release gate.

The submission endpoint performs its own authentication: it loads the private gate's current challenge, owner key and immutable policy, then verifies the genuine owner endorsement and genuine candidate signature with the existing protocol. It accepts no supplied policy, key, challenge payload or owner identity. The submission can only append public evidence to a new private table; it cannot register a reviewer, attest independent custody, issue a grant, release Oracle or run a device command. Owner retrieval additionally requires the original confirmed-account JWT session and matching owner UUID. No owner token or private key goes into PowerShell or the new ledger.

No, expiry, key rotation/revocation, a consumed challenge, completed registration, another privileged reviewer or an altered held intent closes the transport. The SQL boundary rechecks under row locks and refuses stale evidence. Identical submissions are idempotent, conflicting receipts cannot overwrite an earlier receipt, and the receipt table is append-only with all authority flags false. Direct anon/authenticated table and function access is denied.

The updated command reuses an existing exact-nonce public proof instead of asking the signer to overwrite it. It never copies the JSON back through the clipboard. The original protected signer, pinned source hashes, challenge lifetime, owner signing key origin, notification service and production release gate are unchanged. Existing old proofs remain historical receipts; they cannot be used for a new challenge.

Tests: `node --test test_proof_transfer.mjs`; real local-only PostgreSQL `python3 test_proof_ledger.py`; guided owner-page tests additionally verify automatic proof retrieval, forged-transfer rejection, expiry and a distinct Finish action. The database suite deliberately uses synthetic records and does not claim that SQL verifies signatures; the real-signature Node suite tests that preceding boundary.

Deployment: apply schema, deploy the separate proof function including the canonical sibling first_reviewer_protocol.mjs at its existing relative path, then update only the existing portal's guided module and extension. Runtime source tests and health are LAB_PASS until an actual current proof is transferred and the owner page receives it. No production proof/signature should be fabricated to test transport.

Rollback: restore the recorded previous portal alias, and deploy an inert proof-transfer endpoint if needed. Keep the append-only public receipts for review. No change or rollback to the existing release gate or phone notification publisher is needed.

Error/fix log: the owner created a valid-looking local proof but clipboard transfer was not independently confirmed. Rerunning the signer then failed EEXIST because the proof was already present. A screenshot exposed the public proof, but the handoff crossed the original challenge deadline; it was not registered. The repair removes the clipboard step and reuses saved public evidence only for its exact fresh nonce. It does not extend expiry or create a new key.
